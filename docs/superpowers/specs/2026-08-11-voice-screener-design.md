Дата: 2026-08-11
Автор: Павел Харитонов
Статус: утверждён к реализации

---

## 1. Задача и критерий успеха

Агент голосом проводит первичный скрининг кандидата на английском и отдаёт рекрутеру
карточку, по которой тот за минуту понимает: подходит ли кандидат и что перепроверить лично.

Оценивается **форма ответа, не содержание**. Три вещи:

1. **Структурность** — отвечает ли человек на заданный вопрос; есть ли в примере
   «ситуация → что сделал → результат».
2. **Уровень языка (CEFR)** — обоснованно, с опорой на конкретные фрагменты речи.
3. **Манера речи** — говорит свободно, зачитывает заранее подготовленное или ищет
   ответ в другом окне во время паузы.

**Каждое утверждение в карточке подкреплено ссылкой на момент разговора.** Утверждение
без опоры на конкретный фрагмент в карточку не попадает — оно и есть то, от чего мы уходим.
Решение по кандидату принимает человек; карточка показывает, на что посмотреть.

### Принимающие критерии

- Демо открывается по ссылке и работает без локальной сборки, без ключей у проверяющего.
- Сквозной путь целиком: интервью → анализ → карточка → дашборд. Не три экрана и заглушка.
- Не по счастливому пути тоже работает: см. §8.

## 3. Архитектура

```
КАНДИДАТ (EN)                                   РЕКРУТЕР (RU)
     │                                                │
     ▼                                                ▼
/  →  /interview                                 /dashboard → /card/[id]
     │                                                │
     │ 1. consent-экран (имя + согласие на запись)     │ карточка:
     │ 2. проверка микрофона                          │ • стоп-факты + цитаты
     │ 3. POST /api/session → эфемерный ключ           │ • структурность
     │ 4. WebRTC напрямую к OpenAI Realtime            │ • CEFR (или «мало данных»)
     │                                                 │ • манера речи
     ├──► реплики + тайминги ──► POST /api/turns ──────┤ каждое утверждение →
     │    (каждые 4 сек, инкрементально)               │ цитата → клик → фрагмент
     │                                                 │   играется через Web Audio
     ├──► аудио: mic + голос агента → MediaRecorder    │
     │    чанки ~15 сек ──► напрямую в Vercel Blob     │
     │                     (+ POST /api/audio/register) │
     │                                                 │
     ▼ конец разговора: POST /api/turns { done: true } │
     │                                                 │
СЕРВЕР доводит до конца сам (клиента может уже не быть)│
     │                                                 │
     ├─ prepareAudio: склейка чанков → ремукс          │
     │   → перематываемый файл с длительностью          │
     │                                                 │
     └─ runAnalysis:                                   │
        ├─ шаг 0 (код): нейтральные метрики,           │
        │   порог достаточности речи                    │
        ├─ шаг 1 (LLM, strict JSON, параллельно):      │
        │   структурность │ CEFR │ манера │ факты       │
        ├─ шаг 2 (код): проверка цитат по транскрипту, │
        │   утверждения без опоры выбрасываются         │
        ▼                                              │
   Neon Postgres (sessions) ───────────────────────────┘
   Vercel Blob (чанки + перематываемая запись)
```

Ключевое свойство: **постоянный ключ OpenAI никогда не покидает сервер**. Браузер получает
короткоживущий эфемерный ключ из `/api/session` и только с ним идёт в OpenAI.

---

### 3.1 Контракт с OpenAI Realtime (проверено по документации 11.08.2026)

| Что | Как именно |
|---|---|
| Эфемерный ключ | `POST https://api.openai.com/v1/realtime/client_secrets`, тело `{ session: { type: "realtime", model, instructions, audio, ... }, expires_after: { seconds: 120 } }`; берём `.value` |
| Модель | `gpt-realtime-2.1`, `reasoning.effort: "low"` (рекомендация докуменатции для голосовых агентов) |
| WebRTC handshake | SDP-оффер: `POST https://api.openai.com/v1/realtime/calls`, `Content-Type: application/sdp`, `Authorization: Bearer ek_...`; ответ — сырой SDP-текст. Без `?model=` |
| Канал событий | data channel строго с именем `oai-events` |
| Транскрипция кандидата | **по умолчанию выключена**; включаем `session.audio.input.transcription.model = "gpt-4o-transcribe"` |
| Определение конца реплики | `semantic_vad`, `eagerness: "low"` (потолок 8 сек) — кандидат думает над ответом, и обрывать его нельзя |
| Лимит сессии | 60 минут, продлить нельзя. Наше интервью ~10 минут |

Эфемерный ключ живёт 120 секунд и **не одноразовый**; конфиг сессии, привязанный к нему,
клиент технически может переопределить. Поэтому рубрика оценки в инструкциях разговора
не живёт — вся оценка происходит на сервере в `/api/analyze`, куда клиент не достаёт.

Два места, которые проверяем эмпирически в первый же день: приходят ли `audio_start_ms`
с `semantic_vad` (если нет — переключаемся на `server_vad` с `silence_duration_ms: 1500`,
что тоже не режет думающих) и совпадает ли `item_id` в VAD-событиях и транскрипции.
От первого зависит выбор VAD, от второго — вся привязка цитат, поэтому проверка идёт
раньше любого UI.

## 4. Флоу кандидата (EN)

### 4.1 До разговора

1. `/` — что это, сколько займёт (~10 минут), что понадобится микрофон.
2. **Consent-экран** — имя кандидата + явный чекбокс: разговор будет записан и
   расшифрован для оценки рекрутером. Без согласия интервью не начинается (требование ТЗ).
3. Проверка микрофона — кандидат видит индикатор уровня и подтверждает, что его слышно.

### 4.2 Разговор (~8–12 минут)

Сценарий из JSON-конфига роли (`config/roles/*.json`):

1. Агент представляется, ~30 секунд о компании и роли.
2. Фиксированный набор вопросов:
   - локация и право на работу;
   - опыт в нужном домене + **один конкретный пример из практики**;
   - ожидания по формату работы;
   - срок выхода.
3. Вопрос кандидата → ответ из FAQ конфига или честное «рекрутер вернётся с ответом».

**Уточнение вглубь, а не список вслепую.** На каждый ответ агент делает 1–2 фоллоу-апа:
если пример без результата — спрашивает результат; если ответ мимо вопроса — переспрашивает
один раз, затем идёт дальше и помечает это. Лимит фоллоу-апов зашит, чтобы разговор
не растягивался.

### 4.3 После разговора

Экран «Thank you» — что будет дальше. Здесь же ссылка на карточку: это демо, и
проверяющий должен увидеть результат сразу, без похода в дашборд. В продакшене
кандидат карточку не видит — это отмечено в разборе решений.

## 5. Данные разговора

Из Realtime-событий накапливаем список реплик:

```ts
type Turn = {
  id: string       // itemId из Realtime; на него ссылаются цитаты в карточке
  speaker: 'agent' | 'candidate'
  text: string
  tStart: number   // секунды от начала аудио сессии
  tEnd: number
  timingSource: 'server' | 'client'
}
```

### Откуда берутся тайминги (проверено по документации)

**Реплики кандидата — тайминги точные, от сервера.** События
`input_audio_buffer.speech_started` и `speech_stopped` несут `audio_start_ms` и
`audio_end_ms` — миллисекунды от начала аудио сессии — и оба содержат `item_id`.
Тот же `item_id` приходит в `conversation.item.input_audio_transcription.completed`
вместе с текстом. Склейка по `item_id` даёт готовое «эта фраза — с 12.40 по 15.90 секунду»:

```
speech_started { audio_start_ms: 12400, item_id: "msg_7" }
speech_stopped { audio_end_ms:  15900, item_id: "msg_7" }
transcription.completed { item_id: "msg_7", transcript: "I led a team of six" }
```

Это устойчиво к сетевым задержкам и к тому, что транскрипция приходит асинхронно —
в отличие от замера по часам клиента. **Цитируем мы именно кандидата, поэтому
доказательная база карточки стоит на серверных таймингах.**

**Реплики агента — таймингов в API нет**, ни на одном событии ответа. Их выводим
на клиенте по позиции воспроизведения аудио агента и привязываем к той же шкале,
запомнив соответствие «часы клиента ↔ `audio_start_ms`» на первом `speech_started`.
Тайминги агента нужны только для расчёта пауз и для навигации по транскрипту —
не для доказательств, поэтому меньшая точность здесь допустима. В данных
это различие видно явно через `timingSource`.

**Пословных таймингов нет.** Событие `...transcription.segment` со `start`/`end`
в схеме есть, но ни одна realtime-модель его, по документации, не отдаёт, и
документация в этом месте сама себе противоречит. Строим на пофразных таймингах;
цитата = реплика или её часть с границами реплики.

Привязка реплик к вопросам конфига делается **на этапе анализа**, а не во время разговора:
агент может задать вопросы не в том порядке или переформулировать, и попытка вести это
состояние на клиенте — лишняя сложность с шансом разъехаться с реальностью.

### Как транскрипт попадает на сервер

Клиент отправляет реплики **инкрементально**, по мере готовности (`POST /api/turns`),
а не одним куском в конце. Закрытая вкладка на 7-й минуте теряет последнюю реплику,
а не весь разговор.

Тот же роут с признаком «разговор закончен» **сам запускает анализ на сервере**.
Клиент анализ не дёргает: иначе закрытая вкладка и прерванная сессия остались бы
без карточки вовсе, а спек обещает карточку из частичных данных. Запрос на закрытии
вкладки уходит через `sendBeacon` — браузер его доставит, даже когда вкладки уже нет,
и сервер доведёт анализ до конца сам. Страница карточки держит вторую попытку:
если сессия почему-то осталась без карточки, анализ запускается при её открытии.

Документация описывает и более надёжный путь — серверное подключение к той же сессии
по `call_id` из заголовка `Location` SDP-ответа: транскрипт и тайминги пишутся на сервере,
клиент их не касается. Мы этот путь **не берём**, и вот честная причина: он требует живого
WebSocket на всё интервью, а на Vercel функции ограничены по времени выполнения — на
десятиминутном разговоре это отдельный риск и второй путь сбора данных в придачу к
клиентскому. Цена отказа: клиент технически может подменить свой транскрипт. Для
инструмента найма это существенно, поэтому пункт назван в разборе решений как первое,
что надо переделать при выходе в прод.

### Стоимость разговора

Пофакту: аудио на вход $32/1M токенов, на выход $64/1M, при 1 токене на 100 мс речи
кандидата и на 50 мс речи агента; транскрипция кандидата — отдельно $0.006/минуту.
Нижняя граница выходит около $0.02 за минуту речи кандидата и $0.08 за минуту речи
агента, но реальная цена выше и растёт нелинейно: на каждый ответ модели передаётся
весь разговор целиком. Главный рычаг — кэш аудио ($0.40/1M, в 80 раз дешевле), поэтому
инструкции и набор инструментов посреди сессии не меняем: это сбивает кэш.
Точную цифру снимаем замером на первом же полном прогоне и кладём в разбор решений —
заказчику нужна честная стоимость скрининга, а не «это дешевле рекрутера».

Из этого код (не LLM) считает нейтральные метрики: длительность разговора, доля речи
кандидата, распределение пауз «конец вопроса → начало ответа», длина ответов.

Метрики подаются в анализ как **факты**, а не как оценки. Темп речи не считаем и не
показываем — оценка по темпу запрещена (§9).

## 6. Запись аудио

`AudioContext` смешивает микрофон кандидата и **удалённый трек агента из `pc.ontrack`**
в один поток через `MediaStreamAudioDestinationNode`. Писать только микрофон нельзя —
голос агента приходит отдельным медиа-треком и потерялся бы.

**Один рекордер с чанками по ~15 секунд.** Обрыв на 7-й минуте теряет максимум 15 секунд,
а не всю запись. Спецификация W3C нормативно гарантирует, что склейка всех чанков одной
записи проигрывается; чанки разных записей склеивать нельзя, поэтому рекордер на сессию один.

**Ремукс на сервере.** `MediaRecorder` пишет поток, а не файл: индекса позиций (Cues)
в его выводе нет никогда, а длительности нет у всего, что писалось чанками. Поэтому после
разговора сервер прогоняет запись через ремукс копированием пакетов — без перекодирования,
без ffmpeg — и получает файл с длительностью, индексом и SeekHead. Прерванные сессии
проходят тот же путь, так что запись пригодна у всех.

Аудио грузится **напрямую в Vercel Blob клиентским токеном** (`upload()` из
`@vercel/blob/client`, токен выдаёт роут `/api/blob-token`), а не через serverless-функцию:
лимит на тело запроса в 4.5 МБ делает загрузку насквозь нерабочей. URL каждого чанка
клиент регистрирует сам, отдельным запросом — вебхук `onUploadCompleted` на localhost
не срабатывает, и завязка на него означала бы, что аудио проверяемо только на проде.

**Синхронизация времени.** На первом событии начала речи фиксируется соответствие
«время записи ↔ серверные миллисекунды», и дальше тайминги кандидата ложатся на запись
без накопления ошибки. Фрагмент играется с подушкой ±0.4 секунды по краям.

**Воспроизведение фрагмента — через Web Audio, не перемоткой.** По стандарту HTML,
если запрошенная позиция не попадает в доступный для перемотки диапазон, браузер молча
переходит на ближайшую и сообщает об успехе. На странице, которая существует ради
доказательств, это худший из возможных сбоев: цитата играет не те слова, и ни одной
ошибки в консоли. Поэтому карточка один раз скачивает и расшифровывает запись, а затем
играет точные диапазоны по семплам — от индексов контейнера это не зависит вовсе.
Плеер полной записи остаётся обычным: там ремукс уже дал и длительность, и перемотку.

## 7. Анализ (`POST /api/analyze`)

Идемпотентный: повторный вызов для той же сессии не создаёт дубликат, а перезаписывает
результат. Нужен для кнопки «повторить анализ» (§8).

### Шаг 0 — метрики (код)

Считаются детерминированно из `Turn[]`, см. §5.

### Шаг 1 — три параллельных LLM-вызова, structured outputs

Каждый вызов получает транскрипт с идентификаторами реплик и обязан возвращать
`evidence: turnId[]` для каждого утверждения.

**A. Структурность.** По каждому вопросу конфига: ответил ли кандидат на заданный вопрос
(да / частично / ушёл в сторону); в примере из практики — присутствуют ли ситуация,
действие, результат (каждый элемент отдельно, с цитатой); собраны ли все четыре факта.

**B. CEFR.** Диапазон (например B2–C1) + подшкалы: грамматика, словарь, связность речи.
Каждая подшкала — оценка + цитаты, которые её обосновывают. Только текстовые сигналы:
сложность конструкций, точность лексики, связки, самокоррекция. Оценка выдаётся
диапазоном, а не одной буквой — 10 минут разговора не дают точности до подуровня,
и честнее это показать.

**C. Манера речи.** Отличаем живую речь от заранее подготовленной/зачитанной по
текстовым признакам: письменный синтаксис без дисфлюэнсий, резкая смена регистра между
ответами, ответ невпопад после паузы, шаблонные формулировки в неподходящем месте.

Формулируется как **«на что посмотреть рекрутеру»** с уровнем уверенности, а не как
вердикт. Пауза сама по себе сигналом не является — интроверт и читающий с листа звучат
похоже; правило зашито и в промпт, и в проверку результата.

### Шаг 2 — валидация (код)

- Утверждение без `evidence` **выбрасывается** — это ядро всей задачи.
- Каждая цитата проверяется точным вхождением в текст указанной реплики: не сошлось —
  утверждение выбрасывается (защита от галлюцинаций).
- Требование «минимум одна цитата» живёт **в коде, а не в схеме ответа модели**:
  схема, обязывающая приложить цитату к каждому полю, вынуждает модель выдумать её
  там, где сказать нечего. Пусть лучше вернёт пустой список, а код решит.
- Результат складывается в Postgres, статус сессии → `analyzed`.

### Порог достаточности данных

Кандидат может ответить одним словом, перейти на русский или завершить разговор через
минуту. Оценка «B2» по сорока секундам речи — это ровно та необоснованность, от которой
задача уходит, поэтому объём английской речи кандидата считает код, и ниже порога
(меньше ~60 секунд речи или меньше трёх реплик) блок показывает **«недостаточно данных
для оценки»** вместо буквы или вывода. Порог применяется к каждому блоку отдельно:
фактов может хватить, а на уровень языка — нет.

## 7.1 Что видит рекрутер

**Карточка `/card/[id]`** — русский интерфейс, цитаты остаются на английском как есть:

1. Шапка: имя, роль, дата, длительность разговора, статус.
2. Собранные факты: локация, право на работу, опыт, формат, срок выхода — каждый
   с цитатой; чего не прозвучало, помечено как не прозвучавшее, а не додумано.
3. Три блока оценки формы речи: структурность, уровень языка, манера.
4. Свёрнутые полный транскрипт и полная запись.
5. Дисклеймер: что система не оценивает и что решение принимает рекрутер.

Каждая цитата — кнопка: клик играет её фрагмент записи.

**Цифры пауз на карточку не выводятся.** Они считаются и идут в анализ как нейтральный
контекст, но «пауза 8.4 секунды» на экране читается рекрутером как минус — а трактовать
паузу как негативный сигнал спек запрещает. Из числовых характеристик разговора рекрутер
видит только его длительность.

**Дашборд `/dashboard`** — таблица всех сессий со статусами и ссылками на карточки.
Именно она даёт то, чего нет сейчас: сравнимость кандидатов между собой.

## 8. Сбои

Приёмка пойдёт не по счастливому пути — это заявлено прямо. Ожидаемое поведение:

| Сбой | Поведение |
|---|---|
| Нет доступа к микрофону | Понятный экран с инструкцией и retry |
| Обрыв сети во время интервью | Один автоматический реконнект; не вышло → сессия `interrupted`, карточка строится из частичных данных с плашкой «прервано на N-й минуте» |
| Кандидат молчит | Агент переспрашивает; после второго молчания предлагает завершить |
| Кандидат отвечает не на английском | Агент вежливо возвращает разговор на английский; факт попадает в карточку |
| Анализ упал | Статус `failed`, на карточке кнопка «повторить анализ» |
| Кандидат закрыл вкладку | Сессия остаётся в дашборде как `interrupted`, аудио-чанки уже в Blob |
| Кончилась квота OpenAI | Честная ошибка до старта интервью, а не посреди разговора |
| Прямой заход на несуществующий `/card/[id]` | 404 с понятным текстом |
| Кандидат отвечает односложно или почти молчит | Блоки оценки показывают «недостаточно данных», а не выдуманную букву |
| Разговор идёт дольше 15 минут | Агент завершает сам, карточка строится по тому, что есть |
| Слишком много прогонов подряд | Мягкий лимит на число сессий в час: честный экран «попробуйте позже» вместо сгоревшей квоты посреди чужого интервью |

## 9. Границы: чего система не делает

Явные запреты из ТЗ, зашитые в промпты и проверяемые:

- **не оценивает акцент, темп речи, пол, возраст** — дискриминация и юридический риск;
- **не записывает разговор без согласия** — без чекбокса интервью не стартует;
- **не считает паузу негативным сигналом сама по себе.**

На карточке — дисклеймер с этим списком и с тем, что решение принимает рекрутер.

Вне рамок этой версии: интеграция с ATS, многоязычность, автопереход кандидата
на следующий этап.

## 10. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Фронт + бэк | Next.js 15 (App Router, TS, Tailwind) | Один деплой, API-роуты для ключей и анализа |
| Хостинг | Vercel | Деплой из репозитория, ключи в env на сервере |
| Голос | OpenAI Realtime, `gpt-realtime-2.1` (WebRTC) | Прямое соединение из браузера = минимум звеньев и низкая задержка |
| Клиент голоса | `@openai/agents-realtime` | Официальный SDK для браузера; под капотом тот же `POST /v1/realtime/calls`, так что при необходимости сходим на сырой `RTCPeerConnection` |
| Ключи | `openai` npm на сервере | В браузерном пакете WebRTC-хелпера нет; на сервере им же выпускаем эфемерные ключи |
| Анализ | OpenAI `responses.parse()` со Zod-схемами | Тот же провайдер и ключ; схема гарантирует форму ответа и валидируется на месте, без ручного разбора JSON |
| БД | Neon Postgres | Serverless, JSONB под карточку, есть на Vercel |
| Аудио | Vercel Blob, клиентская загрузка | Нативно для Vercel; прямая загрузка обходит лимит на тело запроса функции |
| Ремукс записи | `mediabunny` | Дописывает длительность и индекс позиций копированием пакетов; без перекодирования, без ffmpeg, без зависимостей |

Аутентификации в демо нет — дашборд открыт по ссылке. Это осознанный срез объёма,
он назван прямо в разборе решений, а не спрятан.

## 11. Модель данных

Одна таблица `sessions`:

| Поле | Тип | Назначение |
|---|---|---|
| `id` | uuid | Он же в URL карточки |
| `candidate_name` | text | С consent-экрана |
| `role_id` | text | Какой конфиг роли использован |
| `consent_at` | timestamptz | Когда дано согласие на запись |
| `status` | text | `live` / `interrupted` / `analyzing` / `analyzed` / `failed` |
| `started_at`, `ended_at` | timestamptz | Длительность |
| `transcript` | jsonb | `Turn[]` |
| `metrics` | jsonb | Метрики шага 0 |
| `card` | jsonb | Результат анализа после валидации |
| `audio_chunks` | jsonb | Список URL чанков по порядку |

Карточка целиком в JSONB: форма отчёта ещё будет меняться по ходу, миграции на каждое
поле в двухдневном проекте не окупаются.

## 12. Проверка

- **Unit** — валидация evidence (утверждение без цитаты выбрасывается; цитата, которой
  нет в транскрипте, выбрасывается), расчёт метрик, калибровка таймингов.
- **Фикстуры анализа** — три зафиксированных транскрипта: структурный сильный кандидат,
  слабый, «зачитывающий подготовленное». Прогон анализа не должен путать их местами.
- **Smoke e2e** — консент → сессия создана → карточка отдаётся.
- **Ручной сквозной прогон** — минимум два полных интервью на задеплоенном демо перед
  сдачей, один из них с намеренным обрывом сети.

## 15. Известные слабые места (пойдут в DECISIONS.md)

- **Нет аутентификации** — дашборд и карточки открыты по ссылке.
- **Аудио лежит в публичном хранилище** — по прямой ссылке запись доступна всякому,
  кто её знает, хотя ссылка неугадываема. В проде это приватный доступ с подписанными
  ссылками; для демо цена честно названа здесь.
- **Расшифрованная запись держится в памяти браузера** — на десять минут речи это
  порядка 38 МБ при 16 кГц. Для страницы, открытой на минуту, приемлемо; для длинных
  разговоров пришлось бы резать фрагменты на сервере.
- **Транскрипт собирается на клиенте** — технически подменяем. Правильное решение
  (серверное подключение по `call_id`) описано в §5 вместе с причиной отказа;
  это первое, что надо переделать при выходе в прод.
- **Тайминги реплик агента приблизительные** — в API их нет, выводим по воспроизведению.
  Доказательства цитат это не затрагивает: они стоят на серверных таймингах кандидата.
- **Цитата — это реплика, не слово** — пословных таймингов realtime-модели не отдают,
  поэтому фрагмент играется целой фразой с паддингом ±0.4 секунды.
- **CEFR по 10 минутам разговора** — диапазон, а не точная оценка; это ограничение
  формата, не реализации, и оно показано на карточке.
- **«Ищет ответ в другом окне»** — сигнал вероятностный: мы не следим за экраном
  кандидата и принципиально не хотим. Даём рекрутеру повод послушать фрагмент,
  а не вердикт.
- **Одна роль в демо** — конфиг поддерживает несколько, но настроена и проверена одна.
